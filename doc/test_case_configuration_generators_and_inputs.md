## 1. The Role of Configuration in FUT

The execution of FUT test cases relies on two elements:

1. **Test Case Scenarios:** The logic implemented in `test/*_test.py` files.
2. **Test Case Configuration Parameters:** The inputs that drive the test scenarios, such as channel numbers, security
modes, etc.

These configuration parameters are dynamically generated by configuration generators which process configuration inputs.

- **Configuration Generators:** Located in `framework/generators`, these are Python classes (e.g., `DefaultGen`) that
transform inputs into the final parameters used by `pytest`.
- **Configuration Inputs:** Python dictionaries located in `config/test_case/` that define the data for the generators.

This system allows for flexible and scalable test case creation, where generic test definitions can be easily customized
for specific device models or platforms. The generators also load the model properties file to customize the input
parameters for every specific device model.

The generic inputs are located in `config/test_case/generic/MODULE_inputs.py` files and are used in all cases, unless
specifics exist in platform specific `config/test_case/platform/<PLATFORM>/MODULE_inputs.py` files or model specific
`config/test_case/model/<MODEL>/MODULE_inputs.py` files.

**Note:** A file containing the generated test parameters is created every test run. The file is located here:
`config/test_case/full_test_config.json`

## 2. Generating Test Case Parameters

### 2.1. Basic Structure of Test Inputs

The simplest test case input is an empty dictionary, which generates a single test configuration with no arguments.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {},
}
```

**Generated Configuration Parameters:**

```python
{
    "TESTNAME": [
        {},
    ]
}
```

### 2.2. Defining Test Arguments with `args_mapping`

To create multiple test configurations with different arguments, use the `args_mapping` and `inputs` keys.
`args_mapping` defines the parameter names, and `inputs` provides the corresponding values.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "args_mapping": ["animal", "favorite_thing"],
        "inputs": [
            ["cat", "sleep"],
            ["dog", "human"],
            ["dog", 10],
        ],
    },
}
```

**Generated Configuration Parameters:**

```python
{
    "TESTNAME": [
        {"animal": "cat", "favorite_thing": "sleep"},
        {"animal": "dog", "favorite_thing": "human"},
        {"animal": "dog", "favorite_thing": 10},
    ],
}
```

### 2.3. Using the `default` Key for Common Arguments

To apply the same key-value pair to all generated configurations for a test case, use the `default` key.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "default": {"pet": True},
        "args_mapping": ["animal", "favorite_thing"],
        "inputs": [
            ["cat", "sleep"],
            ["dog", "human"],
        ],
    },
}
```

**Generated Configuration Parameters:**

```python
{
    "TESTNAME": [
        {"animal": "cat","favorite_thing": "sleep", "pet": True},
        {"animal": "dog", "favorite_thing": "human", "pet": True},
    ],
}
```

### 2.4. Using Fixed Dictionaries for Explicit Control

For fine-grained control, you can provide a list of dictionaries directly to the inputs key, bypassing `args_mapping`.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "inputs": [
            {"color": "red", "temperature": "hot"},
            {"color": "blue", "temperature": "cold"},
        ],
    },
}
```

**Generated Configuration Parameters:**

```python
{
    "TESTNAME": [
        {"color": "red", "temperature": "hot"},
        {"color": "blue", "temperature": "cold"},
    ]
}
```

## 3. Additional Generator Features

### 3.1. Automatic Filtering for Radio Capabilities

The generator can filter test configurations based on the device's capabilities as defined in its `model_properties`
file:

- If `radio_band` is in `args_mapping`, the generator filters out bands not supported by the model.
- If `radio_band`, `channel`, and `ht_mode` are present, it performs a compatibility check for all three against the
  model's supported channels and regulatory domain rules.

**Example**: For a model that only supports 2.4G, 5GL, and 5GU bands, the generator will automatically discard inputs
for 5G and 6G.

### 3.2. Implicit Encryption Parameter

For test cases involving wireless settings, if `radio_band` is present in the inputs, the generator automatically adds
an encryption parameter with a default value of `WPA3`, unless it is explicitly defined in the test inputs.

## 4. Controlling Test Execution: ignore, skip, and xfail

The generator supports special keys to control how `pytest` handles test cases:

- ignore: Prevents the test case or specific configurations from being collected by pytest at all.
- skip: The test is collected but not executed. It will be reported in the skipped category.
- xfail: The test is executed, but its outcome is handled differently.
    - If the test fails, it is reported as xfail (expected failure) and does not fail the overall test run.
    - If the test succeeds, it is reported as xpass (unexpected pass).

**Example**: Ignoring an entire test case:

```python
# Model-specific input file
test_inputs = {
    "TESTNAME": {
        "ignore": {
            "msg": "Test case failing"
        }
    },
}
```

**Example**: Skipping an entire test case:

```python
# Model-specific input file
test_inputs = {
    "TESTNAME": {
        "skip": {"msg": "This test case is not required for this model."}
    },
}
```

**Example**: Marking specific configurations with `xfail`:

```python
# Model-specific input file
test_inputs = {
    "TESTNAME": {
        "xfail": {
            "inputs": [
                [44, "HT40", "5gl"],
                [157, "HT40", "5gu"],
            ],
            "msg": "These configurations are known to be flaky."
        },
    },
}
```

## 5. Managing Known Issues

To track tests that are expected to fail due to known bugs without cluttering test reports, FUT provides a known_issues
mechanism. This is handled separately from regular test inputs because known issues are often version-dependent:

- Known issues are defined in `config/test_case/known_issues/<MODEL>_known_issues.py`.
- The file is a dictionary keyed by firmware version.
- When a test configuration matches an entry in the `known_issues` file for the current firmware version, it is
  automatically marked with `xfail` in pytest. This means it will run, but a failure will not cause the test suite to
  fail.
- The `msg` key will provide a custom message, displayed in the test report. If the key is missing, the default value
`KNOWN_ISSUES` will be displayed.
- The `ticket` key is optional. If provided, it will be displayed in the test report as a clickable link.

**Note:** the `known_issues` keyword is always in plural form, used as the dict key, file name, pytest marker, etc.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "args_mapping": [
            "channel", "ht_mode", "radio_band",
        ],
        "inputs": [
            [6, "HT20", "24g"],
            [44, "HT40", "5g"],
            [44, "HT40", "5gl"],
            [157, "HT40", "5gu"],
            [5, "HT20", "6g"],
        ],
    },
}
```

The known issues file for the `MODEL` in question may look like this:

```python
known_issues = {
    "1.2.3": {
        "TESTNAME": {
            "known_issues": {
                "inputs": [[6, "HT20", "24g", "WPA3"]],
                "msg": "Combination of parameters not supported",
            },
        },
    },
    "4.5.6": {
        "TESTNAME": {
            "known_issues": {
                "inputs": [[44, "HT40", "5gl", "WPA3"]],
                "ticket": "fut.opensync.io/TICKET-456",
            },
        },
    },
}
```

The generated configuration parameters for a tri-band device will depend on the firmware version of the device.

For version `1.2.3`:

```python
{
    "TESTNAME": [
        {
            "channel": 6,
            "encryption": "WPA3",
            "ht_mode": "HT20",
            "known_issues": true,
            "known_issues_msg": "Combination of parameters not supported",
            "radio_band": "24g"
        },
        {
            "channel": 44,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "radio_band": "5gl"
        },
        {
            "channel": 157,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "radio_band": "5gu"
        }
    ],
}
```

For version `4.5.6`:

```python
{
    "TESTNAME": [
        {
            "channel": 6,
            "encryption": "WPA3",
            "ht_mode": "HT20",
            "radio_band": "24g"
        },
        {
            "channel": 44,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "known_issues": true,
            "known_issues_msg": "KNOWN_ISSUES",
            "radio_band": "5gl"
            "ticket": "fut.opensync.io/TICKET-456",
        },
        {
            "channel": 157,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "radio_band": "5gu"
        }
    ],
}
```

**Notice** how the `encryption` parameter needs to be put into the `inputs` key of the `known_issues` dict for
`TESTCASE` due to [3.2. Implicit Encryption Parameter](#32-implicit-encryption-parameter).

## 6. Custom Generator Control Keys

### 6.1 `do_not_sort`

By default, the generator sorts the final test configurations based on their parameter values. To preserve the order
defined in the inputs list, add `"do_not_sort": True`. This is useful when a specific execution order is advantageous.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "args_mapping": [
            "channel", "ht_mode", "radio_band",
        ],
        "do_not_sort": True,
        "inputs": [
            [6, "HT20", "24g"],
            [44, "HT40", "5g"],
            [44, "HT40", "5gl"],
            [157, "HT40", "5gu"],
            [5, "HT20", "6g"],
        ],
    },
}
```

### 6.2. `expand_permutations`

Set `"expand_permutations": True` to automatically generate all possible permutations from inputs that contain lists or
sets for explicit permutations, or tuples for ranges of values.

**Configuration Input:**

```python
test_inputs = {
    "TESTNAME": {
        "args_mapping": ["channel", "encryption", "num_clients"],
        "expand_permutations": True,
        "inputs": [
            [44, {"WPA2", "WPA3"}, (1, 3)], # Range tuple is inclusive
        ],
    },
}
```

**Configuration Output:**

```python
{
    "TESTNAME": [
        {
            "channel": 44,
            "encryption": "WPA2",
            "ht_mode": "HT40",
            "number_of_clients": 1,
            "radio_band": "5g"
        },
        {
            "channel": 44,
            "encryption": "WPA2",
            "ht_mode": "HT40",
            "number_of_clients": 2
            "radio_band": "5g"
        },
        {
            "channel": 44,
            "encryption": "WPA2",
            "ht_mode": "HT40",
            "number_of_clients": 3,
            "radio_band": "5g"
        },
        {
            "channel": 44,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "number_of_clients": 1,
            "radio_band": "5g"
        },
        {
            "channel": 44,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "number_of_clients": 2,
            "radio_band": "5g"
        },
        {
            "channel": 44,
            "encryption": "WPA3",
            "ht_mode": "HT40",
            "number_of_clients": 3,
            "radio_band": "5g"
        },
    ]
}
```

### 6.3 `override`

In some cases, you may need to completely replace a test's configuration for a specific model, for instance, to add a
new parameter that is not in the generic `args_mapping`. The `override` key allows one test input definition to replace
another.

**Configuration Input:**

```python
# Model-specific input file
test_inputs = {
    "TESTNAME_MODEL_SPECIFIC": {
        "args_mapping": ["channel", "ht_mode", "radio_band", "custom_param"],
        "inputs": [
            [6, "HT20", "24g", "custom_value"],
        ],
        "override": "TESTNAME", # This config will replace the default one for TESTNAME
    },
}
```

### 6.4. `severity`

Assigns a severity level to a test case, which can be used for reporting and prioritization. Allowed values are
`trivial`, `minor`, `normal` (default), `critical`, and `blocker`.

## 7. CLI Tool for Testing Configurations

To see the final generated configuration parameters without running a full test suite, you can use the command-line
tool. This is extremely helpful for debugging your input files.

```bash
# From within the Docker container
python3 ./framework/generators/fut_gen_cli.py
```

This command will generate a `<GW_MODEL>_<L1_MODEL>_gen.json` JSON file containing the complete test configuration,
identical to what would be used in an actual test run.
